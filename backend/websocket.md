# WebSocket usage audit

## Executive summary

The application exposes a WebSocket endpoint at `/ws/{chat_id}` for chat-scoped status updates, messages, typing indicators, presence, and ping/pong handling. The intended design is:

1. The API accepts a browser WebSocket connection and stores it in an in-memory chat room.
2. API code and background workers update chat state in PostgreSQL.
3. Events are published to Redis Pub/Sub so the API process can forward worker events to connected clients.

The local, single-process broadcast path can work for messages generated inside the API process. The cross-process path currently does not work end to end. The active endpoint imports the root `websocket_manager.py`, but Redis subscription is implemented only in `utils/websocket_manager.py`. No active code imports the latter manager. As a result, worker status updates published from Dramatiq processes have no listener in the API process and are not delivered to connected clients.

## Components and ownership

### WebSocket routes

There are two registrations for the same path:

- `api/routes/websocket.py` registers `@router.websocket("/ws/{chat_id}")` and supports `user_id`, initial status, `ping`, `get_status`, `get_users`, and `typing` messages.
- `main.py` separately registers `@app.websocket("/ws/{chat_id}")` and only receives and discards client text.

`main.py` includes the router before declaring its duplicate route. FastAPI/Starlette route matching normally resolves the first matching route, so the router endpoint is likely the one clients reach, but the duplicate route is ambiguous and should be removed. The application should have one owner for this URL.

### Active connection manager

`websocket_manager.py` is the manager imported by:

- `api/routes/websocket.py`
- `api/routes/process.py`
- `main.py`
- `utils/chat_status_tracker.py`

It keeps process-local state:

- `active_connections: {chat_id: set[WebSocket]}`
- `connection_metadata: {websocket: {chat_id, user_id, connected_at}}`
- `chat_users: {chat_id: set[user_id]}`

It accepts connections, broadcasts JSON messages, removes sockets when sending fails, and provides helpers for status, progress, chat messages, errors, and completion. It does **not** create a Redis Pub/Sub subscription and its send helpers do not publish to Redis.

### Unused Redis-aware manager

`utils/websocket_manager.py` contains another `ChatConnectionManager`. It adds a Redis listener per chat and its send helpers publish to Redis as well as broadcasting locally. However, no route, process code, or worker imports this manager. It is therefore not part of the active WebSocket path.

### Redis Pub/Sub wrapper

`redis_pubsub.py` defines channels as:

```text
ws:chat:<chat_id>
```

`WebSocketPubSub.publish()` JSON-serializes the message and calls `redis_client.publish()`. `WebSocketPubSub.subscribe()` calls `redis_client.pubsub().subscribe(channel)` but returns the result of `subscribe()` rather than the Pub/Sub object. That return value is an acknowledgement list, not a listener that can call `get_message()`.

The unused manager bypasses `WebSocketPubSub.subscribe()` and creates its own Pub/Sub object, then calls `subscribe()` on it. This avoids the wrapper return-value bug, but it does not make the manager active.

## Current message protocol

Messages sent by the route or manager are JSON objects with a `type`, usually a `chat_id`, and often a `data` object.

### Server-to-client event types

- `status_update`: initial or requested current status from `ChatStatusTracker.get_progress_summary()`.
- `progress_update`: status progress generated by `ChatStatusTracker` through `send_progress_update()`.
- `new_message`: user or assistant message broadcast by `/api/process-link`.
- `user_joined`: emitted when the routed endpoint joins a connection with a `user_id`.
- `typing`: typing indicator forwarded by the routed endpoint.
- `users_list`: response to `get_users`.
- `pong`: response to `ping`.
- `crawl_summary`: published directly by the crawler worker.
- `crawl_error`: published directly by the crawler worker on crawl failure.
- `error` and `complete`: helper event types available on the manager but not currently used by the inspected route/worker flow.

### Client-to-server messages

The routed endpoint parses text as JSON and recognizes:

```json
{"type": "ping"}
{"type": "get_status"}
{"type": "get_users"}
{"type": "typing", "user_id": "...", "is_typing": true}
```

Invalid JSON is silently ignored. Unknown message types are also silently ignored. There is no authentication or authorization check on the `chat_id` or `user_id` query parameter.

## End-to-end flow

### Connection

1. A client connects to `/ws/{chat_id}`.
2. The routed endpoint calls `chat_connection_manager.join()`.
3. The root manager accepts the socket and adds it to the process-local room.
4. If `user_id` is present, it adds that ID to the local presence set and broadcasts `user_joined`.
5. The endpoint reads the current database-backed status and sends one initial `status_update` if a status object exists.
6. The endpoint waits for incoming text indefinitely.

The main route's duplicate endpoint does not send initial status and has no message protocol. Which behavior clients receive depends on route ordering and should not be left implicit.

### API-generated events

`api/routes/process.py` uses the root manager directly to broadcast:

- initial status after chat creation;
- the user message after persistence;
- crawling/processing/question status snapshots;
- the assistant message after persistence;
- answered or failure status snapshots.

These broadcasts work only when the WebSocket and the API request run in the same Python process. The root manager has no Redis publication in these paths.

### Worker-generated events

`utils/chat_status_tracker.py` is synchronous because it writes to PostgreSQL synchronously. When it has a progress update, it imports the root manager and invokes its asynchronous `send_progress_update()`:

- if an event loop is running, it schedules a task with `asyncio.create_task()` and returns immediately;
- otherwise, it creates/runs an event loop around the coroutine.

In a worker process, the root manager has no API WebSocket objects, so its local broadcast is empty. Since this manager does not publish to Redis, worker progress is lost to connected API clients.

The crawler additionally publishes `crawl_summary` and `crawl_error` directly through `WebSocketPubSub.publish()`. Those messages are also lost because the active API manager is not subscribed.

## Worker-by-worker audit

### `workers/crawler_worker.py`

Status sequence:

- `crawling`, 10%: starts the crawl.
- `crawling`, 20%: crawl discovery completes.
- `crawling`, 30%: first document found and processing is queued.
- failure: `mark_failed()` and a direct `crawl_error` Redis publication.

It also publishes a `crawl_summary` after success. The direct Redis events use the expected `ws:chat:<chat_id>` channel, but there is no active subscriber. The worker separately dispatches the first document to processing; `crawler/crawler.py` also appears to dispatch processing after creating a version, so duplicate processing should be verified independently.

### `workers/processor_worker.py`

Status sequence:

- `processing`, 25%: extraction starts.
- `processing`, 40%: cleaning/extraction.
- `processing`, 50%: media extraction.
- `chunking`, 60%: processing is complete and chunking is queued.
- failure: `mark_failed()`.

All progress and failure notifications go through `ChatStatusTracker`, hence the inactive root-manager path in worker processes. No direct Redis event is emitted here.

### `workers/chunker_worker.py`

Status sequence:

- `chunking`, 60%: chunking starts.
- `chunking`, 65%: structure analysis when structured content exists.
- `chunking`, 70%: chunks are being stored.
- `embedding`, 80%: chunking finished and embedding is queued.
- `completed`, 100%: no new chunks were inserted.
- failure: `mark_failed()`.

All notifications go through `ChatStatusTracker`. When existing chunks are found, it sends an embedding job and returns. When no new chunks are inserted, it marks the chat completed without dispatching an embedder job, which is intentional only if all existing chunks are already embedded; that assumption should be checked against `embedding_status`.

### `workers/embedder_worker.py`

Status sequence:

- missing API key: immediately `failed`.
- `embedding`, 80%: embedding starts.
- `embedding`, 82%: pending chunk count is known.
- periodic `embedding`, 82%-96%: chunk progress.
- `completed`, 100%: all chunks embedded or completed with per-chunk failures.
- failure: `mark_failed()` for an actor-level failure.

Per-chunk embedding failures are counted, but the final chat status is still `completed` when one or more chunks fail. This is a workflow/data-quality issue rather than a WebSocket transport bug: clients receive a misleading terminal status if transport is fixed.

## Confirmed bugs and risks

### Critical: worker events do not reach WebSockets

The API endpoint uses `websocket_manager.ChatConnectionManager`, while the Redis listener exists only in `utils.websocket_manager.ChatConnectionManager`. Worker calls to `ChatStatusTracker` import the root manager. Therefore worker progress, failure, and crawler summary events are not forwarded from Redis to API sockets.

### High: duplicate WebSocket route

`/ws/{chat_id}` is registered in both the router and `main.py`. The second endpoint has different behavior and can shadow or be shadowed by the first depending on route order. Remove the duplicate and keep the feature-complete route as the sole owner.

### High: Redis Pub/Sub wrapper has a broken subscribe API

`WebSocketPubSub.subscribe()` returns `pubsub.subscribe(channel)` instead of returning the Pub/Sub object. Any caller expecting to call `get_message()` on its result will fail. The method should subscribe and return the Pub/Sub instance, or be removed in favor of one tested subscription abstraction.

### High: Redis publication is duplicated when using the unused manager

The Redis-aware manager publishes a message and then broadcasts locally. Its own Redis listener receives the same published message and broadcasts it again to the same local sockets. A single API process using that manager would likely deliver duplicate events unless messages carry an origin ID or the local path avoids rebroadcasting its own publication.

### High: Redis listener blocks the event loop

The unused listener calls synchronous `pubsub.get_message(timeout=1.0)` inside an async task. Each call can block the event loop for up to one second, delaying WebSocket receives and sends. Use an async Redis client, or move blocking Pub/Sub reads to a dedicated thread and bridge results into the event loop.

### Medium: listener cleanup leaks Pub/Sub resources

On leave, the unused manager cancels the listener and deletes the dictionary entries, but does not unsubscribe or close the Redis Pub/Sub object. Repeated connections can accumulate resources until the Redis connection is reclaimed.

### Medium: listener restart logic is unsafe

The listener catches an exception and calls `_start_pubsub_listener()` from inside the failing listener task while the old task remains registered in `pubsub_tasks`. This can race with leave/reconnect and create stale or competing tasks. Restart ownership should live outside the listener, with explicit task replacement and cleanup.

### Medium: direct Redis events are not checked for delivery

`WebSocketPubSub.publish()` always returns `True` after calling `redis_client.publish()`, even when Redis is unavailable or the returned subscriber count is zero. `redis_client.publish()` returns `0` on failure. The wrapper should distinguish publication success from no subscribers and Redis failure, while recognizing that Pub/Sub itself does not guarantee durable delivery.

### Medium: status updates can be lost due to fire-and-forget scheduling

When a worker has a running event loop, `ChatStatusTracker._broadcast_update()` schedules `send_progress_update()` and does not await it. A worker can finish or its loop can close before the task publishes/broadcasts. Worker execution is synchronous and normally has no running loop, but this behavior is fragile under alternate runtimes and tests.

### Medium: no replay or durable event stream

Redis Pub/Sub drops messages published before subscription and does not retain events for reconnecting clients. A client can miss progress or terminal events during a network interruption. The initial database status partially repairs this for status, but it does not replay `new_message`, `crawl_summary`, `crawl_error`, or other event types.

### Medium: no WebSocket authorization

Any client that knows a chat ID can connect and receive chat status/messages. The optional `user_id` query parameter is trusted and is used for presence; it is not authenticated. Access to the chat should be checked during the handshake using the application's existing user/session mechanism.

### Low: typing is broadcast to the sender too

The route comment says typing is sent to other users, but `broadcast()` sends to every connection in the room. The sender should be excluded if that is the intended protocol.

### Low: connection cleanup is not fully defensive

`join()` is called before the route's `try` block. If acceptance, presence broadcast, or initial setup fails, the socket may not be cleaned up by the route. Also, `leave(chat_id, websocket)` trusts the route-supplied `chat_id` rather than the stored metadata. Cleanup should be idempotent and use the connection's recorded room when available.

## Is Redis Pub/Sub working correctly?

Redis connectivity itself is wrapped reasonably for the job queue and publication: the client connects at import time, `publish()` returns Redis's subscriber count when available, and failures are logged. The WebSocket Pub/Sub feature is not working correctly as an application feature because:

1. The active manager never subscribes to chat channels.
2. The manager that does subscribe is unused.
3. The public `subscribe()` helper returns the wrong object.
4. Worker status updates do not call a Redis-publishing manager.
5. Direct crawler publications have no active API listener.
6. Pub/Sub provides no replay for disconnected clients.

The channel naming and JSON payload approach are consistent, and the API can still deliver same-process broadcasts through the root manager. That is the working subset.

## Recommended repair order

1. Delete the duplicate `main.py` WebSocket route.
2. Keep one `ChatConnectionManager` implementation and import it everywhere.
3. Add one Redis listener per chat to the active manager, using an async Redis client or a non-blocking thread bridge.
4. Fix or remove `WebSocketPubSub.subscribe()` so its contract returns a usable Pub/Sub object.
5. Define publication ownership: publish once, then deliver locally once; prevent a process from rebroadcasting its own Redis message.
6. Make listener lifecycle explicit: subscribe, task creation, cancellation, unsubscribe, close, and restart.
7. Add focused tests for local broadcast, worker-to-API Redis delivery, malformed Redis payloads, Redis unavailable, disconnect cleanup, duplicate prevention, and reconnect behavior.
8. Add authentication/authorization for the chat before accepting the connection.
9. Persist/replay important events or always reconstruct the client view from database-backed messages and status after reconnect.
10. Decide whether partial embedding failure is `failed` rather than `completed`, then expose that state consistently to clients.

## Minimal target architecture

Workers should never attempt to access API WebSocket objects. They should publish a normalized event to `ws:chat:<chat_id>`. The API process should own all socket connections and run one listener per active chat. The listener should validate and deserialize the event, then call a local-only broadcast method. API-originated events should either publish and rely on the listener for delivery, or broadcast locally and publish with an origin marker that causes the local listener to skip the originating event. The choice must be implemented consistently so each client receives one event.

The database remains the source of truth for current status and persisted messages. Redis Pub/Sub should be treated as a low-latency notification channel, not a durable queue.
